# Assumptions register

| ID | Assumption | Why we believe it | How we'll test it | If wrong | Status |
|---|---|---|---|---|---|
| A-0001 | Agents follow repo rules reliably when rules live in CLAUDE.md + .claude/rules | Worked on the previous prototype | check_structure.py passes every session | Add hooks / CI enforcement | open |
| A-0002 | Postgres (append-only + row-level security) is enough for ledger, scopes and links through phase 3 | Proven pattern; MNEXA ran on SQLite | Phase 1–3 benchmarks and query latency | Add a graph store beside Postgres | open |
| A-0003 | MNEXA's proven results reproduce after porting to the new architecture | Same mechanisms, same frozen tasks | Regression tier (phase 2 gate) | Investigate port drift before any new features | open |
| A-0004 | Python is fast enough; model and DB calls dominate latency | Typical agent workloads | Profile in phase 3 | Rewrite hot paths in Rust | open |
| A-0005 | Tests, CI and merges are reliable outcome signals for coding memory | Objective, automatic | Phase 5 coding track | Add human/reviewer signals | open |
| A-0006 | Coding agents will adopt memory through MCP with minimal setup | MCP is supported by major coding tools | Early user installs | Ship native plugins per tool | open |
| A-0007 | One serialized append at a time per stream (advisory lock, D-0003) gives enough write throughput for agent workloads | Agents write a few events per cycle; streams are per project/user, so hot contention is rare | Phase 1 benchmark: 16 concurrent writers on one stream, local Postgres. **Provisional target (accepted by owner 2026-09-30 as provisional): ≥100 appends/s/stream, p99 < 50 ms. Result must be measured and recorded (Phase 1 gate)** | Batched appends or per-stream sub-sequences (new ADR superseding D-0003) | open |
| A-0008 | A shredded key becomes unrecoverable once the next root-key rotation destroys the old root version (and its separate backup), even though wrapped-key bytes survive in dead tuples, WAL, replicas and backups. *Amended 2026-09-30 per D-0004 amendment 6; the backup-retention framing is superseded* | Wrapped bytes are useless without the root version that wrapped them; destroyed root versions exist nowhere (D-0004 amendments 4, 6) | **Owner-specified test (#20/#20a):** shred a key, then **recover its deleted wrapped bytes from the raw data files or a backup**, rotate the root, destroy the old version, and prove the recovered key no longer unwraps. **Extended (D-0004 amendment 7):** for person and month erasure, recover the deleted data key *and* the old master key from backup, run master rotation then root rotation, and prove neither unwraps. **Crash test:** kill the master-rotation job mid-way; resuming must lose no surviving data key | External KMS (D-0004 custody c); or shorten rotation interval | open |
| A-0009 | Plaintext envelope headers (opaque UUIDs, enums, timestamps, model/tool identifiers) reveal no personal content once payload keys are shredded. *Amended 2026-09-30: model/tool identifiers added per D-0002 amendment 1* | Headers hold opaque ids, fixed enums and charset-restricted short identifiers; a person's identity is always encrypted (D-0002) | Privacy review of every plaintext column at each envelope_version; intake test that non-UUID values in id fields are rejected | Encrypt more header fields and lose indexability for them (new envelope_version) | open |
| A-0010 | The vendored gitleaks rules (under google-re2) plus an entropy check strip the secrets coding agents typically leak, before they reach the ledger. *Reworded 2026-09-30 per D-0007 amendment 3; the earlier single "catch ≥ 99% on known formats" figure is superseded* | Common formats are well known and regular; gitleaks is maintained | Labeled corpus (D-0007 amendments 2–3): seeded generators from providers' documented formats, independent of the rules, output pinned by sha256; committed permissively-licensed negatives, pre-scanned. **Targets:** (1) **each covered provider** (the D-0007 amendment 3 list) and **each generic category** (private keys, DB connection strings, credentials in URLs, JWTs, `.env` assignments) reaches catch rate **≥ 99% individually**; (2) false-positive rate **≤ 2%** on the negatives; (3) **coverage** (covered rules / total rules) reported on its own, with unmeasured rules listed by name; (4) unknown formats (entropy-only) reported separately | Secrets land encrypted in the ledger and need shredding; improve rules or add a dedicated scanner | open |
| A-0011 | Postgres RLS driven by `SET LOCAL` settings isolates scopes correctly under connection pooling, savepoints and nested transactions | `SET LOCAL` is transaction-scoped by definition; FORCE RLS applies to non-owner roles | Phase 1 adversarial RLS suite (D-0005 consequences), run against a real Postgres with a pool | Per-principal DB roles (D-0005 option 3) | open |
| A-0012 | Phase 1 threat model: the app process is trusted to state the calling principal honestly; RLS protects against query bugs and misrouting, not a compromised app | Principal authentication belongs to the interface layer (phase 3) | Revisit when the MCP/API auth ADR is written; a security review names the attacker classes | Per-principal DB roles or a separate auth service (supersede D-0005) | open |
| A-0013 | Tamper-evidence threat model: we must detect accidental corruption and a DB-level editor who lacks the checkpoint signing key; an attacker holding that key is out of scope | Signing key is held outside DB and app role (D-0003) | Phase 1 tests: verify_chain detects edited payload, edited header, deleted row, reordered rows, and a full-stream rewrite with recomputed hashes | Stronger key custody or external witness/transparency log (D-0003 option 3) | open |
| A-0014 | Every event has exactly one natural owning stream; no event must live in two scopes | Cross-scope sharing is explicit promotion (SPEC Law 5), not dual writes | Walkthrough of every coding-agent event kind in SPEC's coding profile before Phase 1 code; revisit on phase 5 coding track | Event references across streams or multi-owner events (supersede D-0005 part a) | open |
| A-0015 | No single DEK encrypts more than 2^28 payloads, keeping random 96-bit GCM nonces far below the collision bound | Keys are per (stream, subject, epoch), so volume is split | Per-key encryption counter; append refuses and forces rotation at 2^28 (test with a lowered limit) | Switch to XChaCha20-Poly1305 or deterministic nonces (new ADR) | open |
| A-0016 | The ML libraries needed in phase 6 (PyTorch and an adapter-training library) support Python 3.14 | Major libraries follow CPython releases within months; 3.14 released Oct 2025 | Before phase 6 design (and cheaply earlier): install the chosen libraries in a clean 3.14 env and run a tiny adapter-training smoke test | Run the personal model as a separate process with its own Python (it is already a separate component per SPEC) | open |
| A-0017 | gitleaks' rules (written for Go RE2) compile and match identically under Python `re` | RE2 syntax is mostly a subset of Python `re` | When #6 is built: compile every vendored rule under `re` **and under `google-re2`** (owner, 2026-09-30); compare per rule id: (a) matches identical to gitleaks' RE2 semantics on the corpus, (b) worst-case time on adversarial untrusted input (catastrophic-backtracking probes). The comparison table goes to the owner as part of resolving this assumption | Add `google-re2` (new dependency ADR) or translate the failing rules explicitly | **invalidated** 2026-09-30: 22/221 rules don't compile under `re`, 1 misread, 10 disagree with Go, 1 exponential (`curl-auth-user`). Evidence: `docs/assumptions/evidence/A-0017-regex-engines.md`. Dependents: D-0007, D-0009 (proposed), INDEX #6 |
| A-0018 | `google-re2` matches gitleaks' Go `regexp` semantics for every vendored rule, in linear time | Same RE2 family; measured 221/221 agreement with Go and 18 ms worst case per 20 KB (A-0017 evidence) | Partly validated by the A-0017 evidence; re-checked by the Go-agreement guard on the #6 labeled corpus (real positives for every rule, including the 22 with thin coverage) | Fall back to D-0009 option 3 (gitleaks binary) | open |
